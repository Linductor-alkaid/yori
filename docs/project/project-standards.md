# Yori 项目管理与工程规范

> 状态：Active
> 版本：1.0（Yori 实例化版）
> 生效日期：2026-09-02
> 适用范围：Yori 的代码、测试、设计、计划、决策、验证记录、发布材料和 Git 仓库操作

本版已按 Yori（单节点多用户 GPU 训练任务排队、调度与进程守护系统）完成实例化与裁剪：
目标平台限定 Linux（NVML、systemd、Unix Domain Socket、`SO_PEERCRED`）；Executor 以
git submodule + 仓库根 `dependencies.lock.json` 方式锁定（见第 9.1 节）；新增仓库级约束以
根目录 [AGENTS.md](../../AGENTS.md) 为准。

## 1. 目的与规范效力

本文定义项目的规划、任务跟踪、技术决策、文档编写、验证取证、Executor 依赖使用、Git 仓库
管理和变更同步规则。目标是让每项工作都能回答：为什么做、由什么设计约束、当前做到哪里、
如何证明完成，以及后续如何复现结论。

仓库内规则按以下顺序解释：

1. 用户或维护者对当前工作的明确要求。
2. 根目录 `AGENTS.md` 中的仓库级强制约束。
3. 本文中的项目管理与工程规范。
4. 已批准的设计文档和决策记录。
5. 总计划、里程碑计划和工作项中的局部约定。

低层文档不得静默覆盖高层约束。若实现需要改变已生效的架构、公开契约、安全边界、Executor
使用方式或产品默认值，必须先新增或更新决策记录，再同步修改设计、计划和测试。

文档承担不同职责，不互相替代：

- 设计文档说明系统应如何工作以及为什么这样设计。
- 决策记录说明一个有实质影响的选择、备选方案和后果。
- 计划文档说明交付顺序、范围、状态、依赖和验收方式。
- 测试及验证记录说明某项声明在什么条件下得到证明。
- 代码和配置是实际行为的实现，但不能作为缺失契约文档的长期替代品。

## 2. 文档目录

文档按用途放置；目录在出现首份对应文档时创建：

| 路径 | 内容 | 典型文件 |
| --- | --- | --- |
| `docs/design/` | 架构、模块、协议、状态机和跨层契约 | `<domain>_design.md` |
| `docs/decisions/` | 架构决策和产品默认值记录 | `DEC-001-<topic>.md` |
| `docs/plans/` | 总计划、里程碑计划和交付清单 | `yori-implementation-plan.md`、`m1-<scope>.md` |
| `docs/security/` | 威胁模型、安全策略、隐私和凭据处理 | `threat-model.md` |
| `docs/compatibility/` | 平台、编译器、依赖和 Provider 兼容性证据 | `<dep>-<version>.md` |
| `docs/supply-chain/` | 依赖锁定、许可证、SBOM 和升级审计 | `dependency-policy.md` |
| `docs/benchmarks/` | 性能目标、方法、原始条件和结果摘要 | `<metric>-latency.md` |
| `docs/executor_feedback/` | Executor 能力缺口反馈台账 | `ledger.md` |
| `docs/project/` | 本规范及其他仓库级协作流程 | 本文 |

不要用一个"总文档"承载所有内容。安全结论、兼容性声明、性能数据和供应链证据应保留在各自
目录，由设计或计划通过相对链接引用。

## 3. 项目规划层级

### 3.1 总计划

总计划是项目交付范围与进度的唯一入口，使用
`docs/plans/yori-implementation-plan.md`。它包含：

- 当前整体状态和最近更新时间。
- 交付边界条目（`SCOPE-NN`）：确认包含与明确不包含的能力，逐条可勾选。
- 不可破坏的架构约束（`RULE-NN`）：分层、所有权、安全、容量和验证底线。
- Executor 并发边界条目（`EXEC-NN`，见第 9 节）。
- 里程碑索引、依赖关系和建议发布点（里程碑应产生可独立验收的能力增量，仅以目录、分工或
  时间周期划分的内容不适合作为里程碑）。
- 尚未冻结的产品或技术决策（`DEC-NN` 暂定默认值）及其负责人和最迟冻结里程碑。
- 跨里程碑通用完成定义（`DOD-NN`）。
- 建议的拆分与合并顺序：先骨架后功能、先契约后实现、先 SPI/假实现后真实依赖。
- 延后项与触发条件（`POST-NN`）：明确什么证据出现时才立项。

总计划保持概览性质。具体任务、测试和逐轮实施证据放到独立里程碑文档，避免总计划因流水
记录而失去可读性。

### 3.2 里程碑计划

每个里程碑使用独立文件，例如 `docs/plans/m1-<scope>.md`，并必须声明：

- 状态、负责人、所属总计划和最后更新时间。
- 目标、范围、非目标、前置依赖和建议发布点。
- 带稳定编号的工作项。
- 测试矩阵和退出条件。
- 风险、阻塞项及相关设计或决策链接。
- 按日期追加的实施与验收记录。

### 3.3 工作项与编号体系

工作项是可验收的最小计划单位，使用 `M<里程碑>-<两位序号>`，例如 `M1-03`。一项工作应描述
结果而非活动：使用“提供可取消的 Task 状态推进并覆盖终态幂等测试”，而不是“研究状态机”。

工作项必须能关联到至少一项验收方式。预计需要跨多个模块、无法由单次评审验证或包含多个
独立结果时，应拆分为多个工作项。

计划内其他编号系列：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `SCOPE-NN` | 总计划交付边界条目 | `SCOPE-01` |
| `RULE-NN` | 总计划不可破坏架构约束 | `RULE-07` |
| `EXEC-NN` | 总计划 Executor 并发边界条目 | `EXEC-05` |
| `DOD-NN` | 总计划通用完成定义条目 | `DOD-08` |
| `POST-NN` | 延后项及其立项触发条件 | `POST-03` |
| `DEC-NNN` | 架构或产品决策记录 | `DEC-004` |
| `BUG-YYYYMMDD-NNN` | 需要跨提交跟踪的重要缺陷 | `BUG-20260831-001` |
| `RISK-YYYY-NNN` | 影响里程碑或发布的已识别风险 | `RISK-2026-02` |
| `EXE-YYYYMMDD-NNN` | 仅用于 Executor 反馈台账 | `EXE-20260830-001` |

编号一经被引用不得复用；项目扩大到编号冲突时可增加领域前缀，但同一文档内必须一致。

## 4. 状态与勾选规则

计划、里程碑和工作项使用以下状态词，不自造含义相近的状态：

| 状态 | 含义 |
| --- | --- |
| `Proposed` | 已提出，范围或方案尚待评审 |
| `Planned` | 范围、依赖和验收方式已明确，可排期 |
| `In Progress` | 已开始实施，尚未满足完成定义 |
| `Blocked` | 有明确外部阻塞，已记录负责人和解除条件 |
| `Completed` | 实现和全部适用退出条件已通过 |
| `Superseded` | 已由另一文档或决策替代，保留历史链接 |
| `Cancelled` | 明确终止且不再计划交付，保留原因 |

决策记录使用 `Proposed`、`Accepted`、`Superseded` 或 `Rejected`：`Accepted` 表示已批准并生效，
`Rejected` 表示经评审未采用。决策状态不用于表示实施进度；其落地进度由关联的计划工作项跟踪。

清单勾选必须遵守以下规则：

1. 只有实现、测试、必要文档和本项验收均完成后，才能从 `[ ]` 改为 `[x]`。
2. “代码已写完”“本机能编译”或“提交已合并”本身不等于完成。
3. 因设备、权限、网络、凭据或平台缺失而未执行的验证必须保持 `[ ]`，不得用 skip、预期通过
   或其他平台的结果冒充成功。
4. 未执行项必须记录原因、所需环境、负责人和可操作的补跑条件。
5. 工作项全部完成不自动关闭里程碑；所有退出条件也必须逐项通过并留下验证记录。
6. 重新打开已完成工作时保留原验证记录，说明失效原因，并将状态或复选框恢复为未完成。

## 5. 准入与完成定义

### 5.1 Definition of Ready

非平凡工作进入 `In Progress` 前至少满足：

- 目标、范围和非目标可被复述且没有关键歧义。
- 所属里程碑或维护任务明确，并已有稳定编号。
- 相关设计、决策和公开契约已定位；需要改变它们时已有同步更新安排。
- 依赖、风险、平台条件和 Executor 承载方式已识别。
- 验收标准可执行，所需测试环境已知。
- 涉及用户数据、凭据或外部副作用时，安全与恢复行为已定义。

小型拼写修复、无行为变化的格式调整等可不创建独立计划项，但仍必须遵守相关文档规则。

### 5.2 Definition of Done

一项变更只有同时满足以下条件才可完成：

- 实现符合分层、所有权、取消、错误和 Executor 生命周期约束。
- 新增或变更行为具有与风险相称的自动化测试。
- 适用的构建、测试、静态检查、平台验证或基准已经执行并通过。
- 公开 API、配置、事件 schema、错误语义和示例已同步更新。
- 受影响的设计、决策、计划、安全、兼容性和供应链文档已同步更新。
- 验证记录包含可复现证据；未验证声明被明确限定。
- 不存在被吞掉的失败、无主异步任务、未闭合取消路径或未登记的 Executor 能力绕行。
- Commit 与 MR 符合第 10 节规范，评审意见已全部回复或处置。

## 6. 文档模板

### 6.1 里程碑文档模板

新建里程碑文件时使用以下基本结构，可按领域增加小节，但不能删除状态、任务、退出条件和
验证记录：

```md
# M1：里程碑名称

> 状态：Planned
> 负责人：姓名或团队
> 所属计划：Yori 实施总计划（创建文件时改为实际相对链接）
> 前置：M0
> 建议发布点：<release-alpha>
> 更新日期：YYYY-MM-DD

## 目标

## 范围与非目标

## 设计与决策依据

## 工作项

- [ ] `M1-01` 以可验收结果描述任务。

## 风险与阻塞

## 测试与退出条件

- [ ] 给出可观察、可执行的通过条件。

## 验证记录

YYYY-MM-DD：记录 commit、环境、命令、结果、限制和剩余项。
```

验证记录按时间追加。可以修正事实错误，但不得重写历史使失败、回退或环境限制消失。

### 6.2 决策记录模板

以下变化必须建立或更新 `docs/decisions/` 中的记录：跨模块依赖方向与生命周期；公开 API、
持久化格式、事件 schema 或兼容性承诺；核心契约；安全边界与默认权限；关键依赖、支持平台、
性能目标或产品默认值；明显改变实现复杂度或未来扩展方向的取舍。

```md
# DEC-NNN：决策标题

> 状态：Proposed | Accepted | Superseded | Rejected
> 日期：YYYY-MM-DD
> 负责人：姓名或团队
> 冻结里程碑：M1
> 替代/被替代：无

## 背景与问题

## 决策

## 备选方案

## 影响与风险

## 验证方式

## 关联文档和工作项
```

尚待确认但为推进验证而采用的选择必须标为“暂定默认值”，同时填写负责人和最迟冻结里程碑，
不能把暂定值写成既定事实。推翻既有决策时，新记录应链接旧记录，旧记录改为 `Superseded`
并反向链接新记录。禁止删除已被代码、计划或发布说明引用的历史决策。

### 6.3 最小变更记录模板

非里程碑性质但需要留存的实施记录可使用：

```md
## YYYY-MM-DD：M1-03 简短结论

- 范围：本次实际改变的行为。
- 依据：关联设计和 `DEC-NNN`。
- 验证：平台、配置、准确命令及结果。
- 限制：未执行项、原因、负责人和补跑条件。
- 同步：已更新的计划、设计、测试及兼容性文档。
```

该记录可以放在对应里程碑的“验证记录”中。不要为每个小提交创建孤立报告；记录粒度应足以
支持里程碑验收、问题定位和结论复现。

### 6.4 Executor 反馈台账条目模板

见第 9.4 节。

## 7. 验证证据

每条重要验收记录应包含：

- 日期和对应 commit 或工作树状态。
- 操作系统、架构、设备或模拟器、编译器和关键依赖版本。
- 构建类型、feature flags 等影响结果的条件。
- 可复现的准确命令或 CI job/run 链接。
- 通过、失败或未运行的结果，以及关键计数或指标。
- 已知限制、失败归属、负责人和补跑条件。

以下声明必须区分证据等级：

| 声明 | 最低证据 |
| --- | --- |
| 源码或配置支持 | 对应代码、配置和静态检查 |
| 可以编译 | 指定工具链和配置的实际构建结果 |
| 可以运行 | 目标环境中的运行或集成测试 |
| 可互操作 | 与明确版本对端的端到端验证 |
| 满足性能目标 | 固定方法、样本、硬件和统计结果 |
| 满足实时性目标 | 延迟分布、调度条件、过载和取消边界实测 |
| 跨平台支持 | 每个被声明平台的构建和适用运行门禁 |

测试 skip 是诊断结果，不是成功证据。日志可以作为附件，但验收记录还应给出人可读的结论，
不能只贴一段无法定位环境和退出码的输出。

## 8. 文档同步矩阵

实现变更时按下表检查同步范围：

| 变更类型 | 必须检查或更新 |
| --- | --- |
| 公开 API、接口或错误语义 | 设计、头文件注释、示例、测试、兼容性说明 |
| 状态机或状态转换 | 设计、状态图、事件 schema、恢复和竞态测试 |
| 并发、取消、定时或 shutdown | 设计、Executor 路由、生命周期测试；能力不足时更新反馈台账 |
| 通信协议或数据格式 | wire 协议设计、golden vectors、兼容性矩阵、fuzz corpus |
| 安全或权限边界 | 威胁模型、决策、负向测试和事件脱敏规则 |
| 产品或技术默认值 | 决策记录、总计划、配置、测试和迁移说明 |
| 依赖版本或构建组合 | 锁定信息、兼容性矩阵、许可证/SBOM 和回归记录 |
| 性能或实时性声明 | benchmark 方法、结果、目标平台限制和计划门禁 |
| 里程碑范围或状态 | 总计划索引、里程碑文档、依赖方和验证记录 |

同步更新应与实现处于同一变更中。确实需要分阶段完成时，相关工作项保持未完成，并记录
后续编号和负责人，不能以“以后补文档”关闭当前范围。

## 9. Executor 依赖使用规范

### 9.1 定位与锁定

Executor（`third_party/executor`，C++20 并发与生命周期库）是项目唯一的并发基础设施。
它以 pinned 依赖形式引入。Yori 采用 **Git submodule + 锁文件**：`.gitmodules` 声明
`third_party/executor`，仓库根 `dependencies.lock.json` 记录 source、精确 commit、版本号、
许可证及许可文件路径；CMake configure 时校验 commit。备选方式（lock 清单 + CMake 拉取，
离线/CI 构建用 `-DYORI_FETCH_DEPENDENCIES=OFF` 走只校验路径）仅在前述方式不可用时经决策
记录切换。

当前 pin：executor `v0.4.0-82-g4fd8e60`（`4fd8e6097879a56c7c3ad33b10f803cfe2e2e4d9`，
origin/master @ 2026-09-02，MIT）。初始引入即直接固定 origin/master，未等待发布 tag；后续
升级沿用本节流程。

未经明确授权不得修改 pinned executor；升级必须记录旧版本、新 commit、能力变化、受影响
范围和回归结果。

### 9.2 强制规则

1. 所有异步任务、延时任务、周期任务、依赖任务、阻塞 I/O worker、实时控制任务及其启动、
   停止、等待和诊断，必须通过 Executor 的公开能力管理。创建、接纳、取消、排空、关闭、
   完成和失败对 Executor 保持可见。
2. 自研代码不得使用 `std::thread`、`std::jthread`、`std::async`、自建线程池、私有定时调度器、
   detached worker 或脱离 Executor 生命周期的 fire-and-forget 工作。平台 API 要求线程亲和时，
   将其封装在 Platform Adapter 中，并通过 Executor 支持的外部事件循环或扩展边界协调。
3. 普通有限任务优先使用 `submit_auto()`，并保留、消费其 `future`。成功入队只表示 admission，
   不等于执行成功；影响任务结果的异常不得被丢弃。
4. 跨执行上下文通信按语义选用 `executor::comm` 组件：逐条 FIFO 用 `MpscChannel`，最新状态
   用 `LatestMailbox`，一致快照用 `DoubleBuffer`，实时路径用 `RealtimeChannel`，多订阅广播用
   `Topic`，启动阶段协调用 `PhaseGate`。不得用 ad-hoc 队列或“共享可变状态 + mutex + 条件变量”
   替代 executor 通信。
5. 长期阻塞 I/O 使用 Executor 的 blocking worker 生命周期能力（如 `start_worker(BlockingWorkerSpec)`
   + 有界工作通道）；允许抖动的后台周期任务使用 timer 能力（`submit_delayed`/`submit_periodic`
   及 `TimerHandle`）；固定周期或低延迟控制使用 realtime/low-latency 能力。不得用普通周期任务
   冒充实时控制。
6. 取消必须是协作式的。优先使用 `submit_cancellable` + `StopToken`/`request_task_cancel`，
   使排队期与运行期取消进入 Executor 生命周期视图。长任务和循环必须定期检查取消状态，并
   保证等待、网络和平台动作具有可解除阻塞的路径。超时不是强制终止，deadline 也不能被当作
   抢占保证；queued soft timeout 不覆盖运行中任务。
7. Executor 必须由明确的外部 owner 初始化和关闭，每个进程的 owner 唯一。关闭顺序为：停止
   任务生产者，发出取消或停止请求，回收 worker/实时路径，等待需要完成的有限任务，最后由
   非 worker 线程执行 `shutdown(true)`。不得从 Executor worker 内完成自等待或最终 teardown。
   组件间不得隐藏全局 Executor 生命周期；依赖通过构造参数或明确 context 传递。
8. 使用 Executor 的监控、状态、失败事件和 `executor::comm` 统计作为任务健康的事实源；新任务
   路径必须使 admission 拒绝、执行失败、超时/取消、背压和生命周期/关闭状态可经 Executor 设施
   观察。不得建立平行任务监控子系统。
9. 队列容量（含 `max_in_flight_tasks` 总量准入）、背压/drop 策略、超时、取消和关闭行为是
   显式设计选择，必须转化为明确结果与事件；不得静默重试、无限排队或吞掉失败。
10. 第三方库回调（网络栈、平台 SDK）只做有界校验和投递，业务 handler 不得直接在第三方
    线程执行；经第三方事件循环的延续派发须遵守集成指南的豁免纪律并保持可追溯。

### 9.3 能力选型与文档路由

设计和实现并发行为前，先使用 pinned 版本自带资源，本地资源与依赖版本一致、优先于其他
版本的文档：

- 应用集成：`third_party/executor/docs/skill/executor-integration/SKILL.md`。按其路由表
  （Quick start / By scenario / By requirement / By API）只加载一个 router 和一张 capability
  card，遵循 card 的集成陷阱，通过其声明的 future/result/status/callback 观察成功。
- 修改 Executor 本体：仅在获得明确指示后使用
  `third_party/executor/docs/skill/executor-maintainer/SKILL.md`，遵循其 source、invariant、
  test 和 documentation 检查。maintainer skill 不是修改依赖的隐式授权。
- 用户指南：`third_party/executor/website/`（zh/en）中 lifecycle、submission、communication、
  monitoring、failure、realtime 与 reliability 各节；公开头文件与 pinned 指南是应用使用的
  权威，优先公共 facade 而非实现细节。

计划与设计必须写明每类工作由 Executor 的哪种能力承载、任务句柄由谁持有、如何取消以及
关闭顺序（总计划 `EXEC-NN` 条目）。

### 9.4 能力缺口与反馈台账

不得为了绕过 Executor 的能力边界而静默引入另一套并发或生命周期设施。当确认 Executor 无法
满足合理需求时，必须执行以下流程：

1. 先核对当前版本的公开头文件、API 文档、集成指南及相关测试，排除 API 选型错误、配置错误、
   平台限制和应用层职责。
2. 在 `docs/executor_feedback/ledger.md` 中新增一条唯一编号（`EXE-YYYYMMDD-NNN`）的反馈记录，
   附上可复现证据、影响范围、期望语义和可验收结果。只写“Executor 不支持”不构成有效记录；
   报告至少包含：缺失的行为、造成缺口的 API/语义限制、为什么现有 lifecycle 与 comm 设施
   不足、建议的最小 Executor 能力或获批例外、延期实施的影响。
3. 在相关代码、测试或设计文档中引用该反馈编号。
4. 确需临时方案时，将其限制在单一 Adapter/compatibility boundary 内，说明行为差异、风险、
   移除条件和测试覆盖。临时方案不得创建线程、队列或调度器，不得改变“任务与生命周期由
   Executor 管理”的总体约束。
5. 未经明确授权，不直接修改 `third_party/executor` 来掩盖集成问题，也不把项目特有策略下沉
   到通用 Executor。等待明确指示后再实施例外或变更依赖。

台账条目分级参考：`P1` 系统性将就（影响整个代码面的派发可见性）、`P2` 结构性将就（某子系统
整体绕开设施）、`P3` 有而未用（应用侧待办，非缺口）、`违规`（应用违反 AGENTS.md 需自行整改）。
每条记录维护状态（`Open`/`Proposed`/`Accepted`/`Resolved`/`Rejected`）和跟进记录表，上游
收敛后回写迁移结论与证据。

以下情况不是 Executor 能力缺口：模型/协议供应商适配、平台手势或 API 映射、业务状态机策略、
错误使用已有 API、平台本身不提供所需权限。它们应在项目对应层解决。

## 10. Git 仓库管理

### 10.1 分支模型与命名

- 采用主干开发模型：`master`（或 `main`）是唯一长期分支，始终保持可构建、可测试。
- 功能工作在短生命周期特性分支上进行，命名 `feat/<scope>-<description>`、`fix/<scope>-<description>`、
  `docs/...`、`refactor/...`、`perf/...`、`test/...`、`ci/...`。
- 特性分支存活时间应尽量短；长期分支须定期同步主干，合并前必须 rebase 或 merge 最新主干
  消除冲突。
- `master` 设为保护分支：禁止直接 push，只能通过 MR/PR 合入，且合入前 CI 必须通过、评审
  必须完成。不得 force-push、改写已发布历史或在未获用户明确要求时重写公共分支。
- 修复紧急问题的 `hotfix/<issue>` 分支从 master 切出，修复后同时合回 master 与进行中的
  发布分支（若存在）。

### 10.2 Commit Message 规范

统一采用格式：

```text
<type>(<scope>): <subject>
```

其中 `scope` 为可选项，用于说明本次修改涉及的模块；同一仓库内部保持一致。Yori 的 scope
词表（按设计文档第 4 节组件命名，新增模块时先扩充词表）：

| scope | 模块 |
| --- | --- |
| `cli` | `yori` 客户端 |
| `daemon` | `yorid` 与其启动/关闭生命周期 |
| `ipc` | Unix Domain Socket 协议、传输与鉴权 |
| `job` | JobManager、JobSpec 与状态机 |
| `queue` | 全局队列与准入 |
| `scheduler` | 调度策略与 GPU lease |
| `gpu` | GpuProvider/NVML adapter 与 GPU 状态 |
| `process` | ProcessSupervisor、进程组与取消 |
| `store` | StateStore/SQLite 持久化与恢复 |
| `launch` | LaunchAdapter/LaunchProfile |
| `observe` | 日志、流式跟随与 TensorBoard 观察接口 |
| `packaging` | systemd unit、安装与发布打包 |
| `deps` | 第三方依赖锁定与升级 |
| `docs` | 仅文档变更（scope 可省略） |
| `build` | 构建系统、预设与 CI（scope 可省略） |

| type | 说明 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | Bug 修复 |
| `refactor` | 代码重构，不改变已有功能 |
| `perf` | 性能优化 |
| `docs` | 文档修改 |
| `test` | 测试相关修改 |
| `build` | 编译系统、依赖相关修改 |
| `ci` | CI/CD 配置修改 |
| `chore` | 其他工程性修改 |
| `revert` | 回滚已有提交 |

推荐优先使用 `feat`/`fix`/`refactor`/`perf`/`docs`/`test`。示例：

```text
feat(controller): add joint command validation
fix(ipc): resolve shared memory initialization failure
refactor(mpc): simplify solver interface
docs: update deployment guide
```

避免含义不明确的提交说明（`update`、`modify`、`fix bug`、`临时修改`、`final2` 等）。

**Commit 颗粒度**：一个 Commit 对应一个相对独立的逻辑修改；不为追求小提交产生大量无意义
提交。开发过程中允许临时 Commit，但提 MR 前应通过 rebase/squash 整理提交历史。

**提交前检查**：

```bash
git status
git diff
git diff --cached
```

确保 Commit 中：只包含本次修改相关内容；不包含无关格式化修改、临时 Debug 代码、运行日志、
编译产物、IDE 临时文件、不必要的大文件，以及密码、Token、Key 等敏感信息。提交中不得携带
与本变更无关的工作树改动。

**提交身份**：`user.name` 与 `user.email` 必须是提交者本人配置，严禁使用他人身份提交。

### 10.3 Merge Request 规范

**标题**：与 Commit 保持类似格式 `<type>(<scope>): <description>`。一个 MR 只解决一个明确的
问题或实现一个完整功能；修改之间没有明显关联时应拆分为多个 MR。

**描述**至少包含四部分：

1. 修改内容：本次 MR 改了什么（如新增模块的行为、参数与工作模式）。
2. 修改原因：为什么需要此次修改（当前缺失或缺陷是什么）。
3. 测试情况：明确说明实际完成的测试（如“编译通过；完成越界指令测试”）。禁止在未执行测试
   的情况下填写“测试通过”。
4. 影响范围：涉及 API/ABI、通信协议、配置文件、参数、数据格式、部署流程、第三方依赖、
   硬件接口或 SDK 接口时逐项说明。

**MR 大小**：保持在 Reviewer 可以理解和有效 Review 的范围内。大型需求按
`基础接口 → 核心实现 → 功能接入 → 测试 → 优化` 拆分；无法拆分的大型重构应提前沟通并在 MR
中说明设计思路和影响范围。

### 10.4 Code Review 与合并

- 原则上至少经过一名相关开发人员 Review。Reviewer 重点检查：实现逻辑、边界条件、异常处理、
  接口兼容性、潜在回归风险、代码可维护性、测试覆盖情况。
- Review 意见明确区分：`必须修改`、`建议修改`、`讨论项`。开发人员完成修改后应回复对应
  comment，避免问题处于未确认状态。
- 合并条件：

```text
开发完成 + 自测通过 + 目标分支已同步 + 无代码冲突 + CI 通过 + Code Review 通过
```

- 合并策略从 `Merge Commit` / `Squash and Merge` / `Rebase and Merge` 中团队统一选择一种：
  普通功能开发推荐 Squash and Merge 保持主线简洁；需要保留完整 Commit 历史的大型功能可按
  实际情况保留。

### 10.5 版本与发布

- 版本号遵循语义化版本（`vMAJOR.MINOR.PATCH`），tag 打在对应发布点 commit 上并附简短说明；
  里程碑文档的“建议发布点”与 tag 一一对应。
- 维护 `CHANGELOG.md`，按版本记录功能、修复、兼容性影响和依赖变化。
- 发布前核对：依赖锁定与 SBOM 可重复生成、许可证清单完整、兼容性矩阵中声明的平台均有
  构建与运行门禁证据、已知限制已写入发布说明。
- 不发布未通过目标平台或基准验证的实时性、性能或跨平台声明。

### 10.6 仓库卫生

- `.gitignore` 覆盖构建目录（`build/`）、生成文件、测试产物、IDE 配置和凭据文件；提交前
  确认 `git status` 无计划外文件。
- 模型、数据集、二进制等大文件使用 Git LFS、对象存储或其他文件管理方案，不直接随普通
  Commit 提交。
- 日志、截图与验证产物过大或含敏感数据时不提交仓库；文档记录受控存储位置、摘要、保留期限
  和复现方法，公开内容提交前必须脱敏。
- 不在远程 URL、进程参数、命令输出或日志中暴露认证 token；凭据经系统 keyring 或受管配置
  注入。

### 10.7 依赖锁定与升级（Git 视角）

- `third_party/` 依赖一律 pin 到精确 commit 并在 lock 文件（`dependencies.lock.json` 或
  `third_party/dependencies.lock`）中登记来源、版本、许可证与校验 commit；configure 阶段
  校验，不匹配即失败。
- 依赖升级走独立 MR：更新 pin、说明版本差异与许可证变化、运行全量回归，并在
  `docs/supply-chain/` 记录审计结论；升级 pinned executor 前先核对第 9.4 节台账状态。
- 生成物（协议文件、fixture、fuzz corpus）约束在构建树内，不进入源码树。

## 11. C++ 工程基线

- 语言标准 C++20；构建统一走 CMake（≥ 3.25）+ `CMakePresets.json`，至少提供 `debug`、
  `release`、`asan`、`ubsan`、`tsan` 预设及对应 `ctest` 入口。
- 以 CMake target 表达依赖方向；公共头不得包含第三方私有类型，用编译测试锁住该边界。
- 仓库根放置 `.clang-format` 与 `.clang-tidy`，CI 执行格式与静态检查；关键警告按仓库策略
  设为 error。
- 测试打标签（`unit`、`integration`、`ipc`、`security`、`recovery`、`fuzz`、
  `performance`、`platform`；需要真实 NVML GPU 的用例额外打 `gpu`，需要多 Linux 用户的
  用例额外打 `multi-user`），CI 不以“无测试可运行”冒充成功；依赖外部环境的用例在缺失时
  显式 skip 并记录补跑条件，核心调度/状态机逻辑通过伪 GpuProvider 与内存 StateStore 覆盖。
- ASAN/UBSAN 常规运行；涉及跨上下文状态、关闭或多进程存储时增加 TSAN/故障注入；新 parser
  或状态机加入 fuzz corpus。
- Yori 目标平台仅为 Linux（依赖 NVML、systemd、UDS、`SO_PEERCRED`）；CI 矩阵至少覆盖
  Linux GCC 与 Clang，执行 configure、build、test 和安装后最小 consumer 编译；不为未验证
  平台声明支持。
- 供应链：所有直接依赖可离线校验，许可证清单与 SBOM（SPDX/CDX）由构建目标再生成。
- 公开 API 变更同步更新示例；示例使用公共 API 并纳入编译或 smoke test。

## 12. Markdown 与链接风格

- 文件名使用小写英文和连字符，稳定编号可保留大写，如 `DEC-001-task-state.md`。
- 标题简洁且层级连续；每个文件只有一个一级标题。
- 使用相对链接连接仓库内文档，链接文字描述内容，不使用“点这里”。
- 表格用于稳定映射和矩阵，长篇论述使用段落或列表。
- 命令、路径、类型、状态和 ID 使用反引号；命令块注明语言 `bash`。
- 日期统一为 `YYYY-MM-DD`，状态和版本在文档开头可见。
- 首次使用缩写时解释含义，公共术语与设计文档保持一致。
- 修改文档后至少检查相对链接、标题结构、代码围栏和被引用文件是否存在。

## 13. 归档与替代

已完成的里程碑和历史决策保留在原路径，以保证链接和编号稳定。文档不再适用时标记
`Superseded` 或 `Cancelled`，在开头写明替代文档、日期和原因。仅在文件从未形成有效引用、
内容完全错误且版本历史足以追溯时才考虑删除。

## 14. 评审与变更控制

评审重点按以下顺序进行：

1. 是否符合产品目标、范围和既有决策。
2. 分层、所有权、平台边界和 Executor 生命周期是否正确。
3. 失败、取消、超时、背压和 shutdown 是否闭合。
4. 安全、隐私、兼容性和迁移风险是否明确。
5. 测试与验证证据是否足以支撑声明。
6. 文档、计划、Commit/MR 规范和状态是否同步。

发现实现与文档不一致时，不能默认以任一方覆盖另一方。先判断是实现缺陷还是已批准的设计
变化：前者修复实现，后者按决策流程同步所有受影响文档。
