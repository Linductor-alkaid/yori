# DEC-005：MVP 全局 FIFO 调度策略

> 状态：Accepted
> 日期：2026-09-04
> 负责人：Linductor-alkaid
> 冻结里程碑：M1
> 替代/被替代：无

## 背景与问题

MVP 需要在单台多 GPU 服务器上为多个 Linux 用户提供唯一、可预测的排队顺序。
设计文档与总计划暂定全局先进先出（First In, First Out，FIFO），但在调度实现前
需要冻结排序、资源不足时的行为，以及与未来公平策略的边界。

## 决策

- 服务器只有一条 authoritative 全局队列，不按用户拆分，也不在 MVP 引入优先级
  或配额。
- 可调度 Job 按 `(submit_time, JobId)` 升序排列；`JobId` 是时间相同情况下的稳定
  决胜键，保证恢复与重复调度得到一致顺序。
- MVP 只接受单 GPU Job。队首 Job 在没有 `FREE` GPU 时保持 `QUEUED`，不得跳过
  队首启动后续 Job；GPU 观测恢复或 lease 释放后由事件重新触发调度。
- FIFO 只决定 Job 选择顺序。GPU lease 建立、外部占用事实和 GPU 选择属于独立资源
  逻辑；瞬时 utilization 不改变队列顺序，也不释放 lease。
- 提交、退出、取消、GPU 状态变化、恢复完成和管理员操作是调度事件；不使用高频
  轮询推进队列。

## 备选方案

- Weighted fair queue：长期多用户公平性更好，但需要用户权重、配额和饥饿处理契约，
  延后到运行记录证明有必要时按 `POST-02` 立项。
- Priority queue：可表达紧急任务，但会引入优先级授权和低优先级饥饿问题，MVP 不采用。
- 队首阻塞时 backfill：能提高异构资源利用率，但多 GPU/显存请求不在 MVP，当前单 GPU
  模型下没有足以抵消顺序复杂度的收益。

## 影响与风险

- 单个用户可以批量占据队列，MVP 接受此限制；通过提交、排队和启动事件保留审计依据，
  达到 `POST-02` 触发条件后再引入 per-user quota 或 weighted fair queue。
- 严格队首顺序优先保证可预测性。未来加入异构或多 GPU 请求时必须重新决策是否允许
  backfill，不得静默改变本决策语义。
- 实现必须保持队列容量有界，容量拒绝是明确结果和事件；该要求由 `M1-04` 验证。

## 验证方式

- `M1-04` 覆盖容量上限、稳定排序和拒绝事件。
- `M1-05` 覆盖事件驱动调度、队首阻塞、lease 建立与释放。
- `M1-07` 覆盖提交到终态的进程内闭环以及恢复顺序一致性。
