# DEC-008：daemon 重启时训练进程存活与日志管道断裂语义

> 状态：Accepted
> 日期：2026-09-08
> 负责人：Linductor-alkaid
> 冻结里程碑：M2（守护语义）；观察面续捕细节最迟 M6 复核
> 替代/被替代：无

## 背景与问题

M2 以管道捕获训练进程 stdout/stderr（设计第 11.2 节）。管道的读端在 `yorid` 进程内，
daemon 退出（包括崩溃）时读端被内核关闭，训练进程后续写管道将触发 `SIGPIPE`。默认
信号处置会直接终止训练进程，等价于"daemon 重启杀死全部训练"，违反 `RULE-10`
（daemon 正常关闭不终止训练进程）。总计划第 6 节要求 M2 补充该守护语义设计。

## 决策

1. **子进程在 exec 前将 `SIGPIPE` 置为 `SIG_IGN`**（fork-exec 窗口内设置，跨 execve
   存活）。daemon 死亡后训练进程继续运行，对已失效管道的写操作返回 `EPIPE` 而不是
   收到致命信号。
2. **daemon 重启窗口内的日志输出不可恢复**：新 daemon 无法重新附加到旧管道。恢复流程
   （M4）以 PID/PGID/启动时间核验进程身份后将其继续标记为 `RUNNING`，但从重启到恢复
   完成之间产生的 stdout/stderr 字节丢失，日志逻辑 offset 不回退，不伪造空档。
3. **日志文件在重启后原文件继续追加**：轮转序号、逻辑 offset 与磁盘文件一一对应，恢复
   后新的输出从既有文件末尾继续（`O_APPEND`），观察面无需特殊迁移。
4. 训练程序自身对 `EPIPE` 的反应（如 Python 未捕获 `BrokenPipeError` 而崩溃）不由
   Yori 兜底；该限制在文档与 `yori submit` 帮助中明示。

## 备选方案

- 保持默认 SIGPIPE 处置：daemon 任何退出都会击杀全部训练进程，直接违反 `RULE-10`，
  否决。
- 训练输出不经管道、直接重定向到文件（daemon tail 文件实现跟随）：daemon 重启对输出
  零影响，但轮转需要配合（重命名后子进程仍持有旧 inode 句柄），`logs -f` 退化为
  tail 实现，且无法实现背压帧协议；作为管道方案的对照保留，若 MVP 运行期发现管道
  方案损失不可接受，以新决策记录切换。
- 常驻最小特权 log-keeper 进程持有读端：彻底消除断裂窗口，但引入第二种守护对象与
  升级路径，复杂度接近 `POST-09`（`yori-launch-helper`），MVP 外。

## 影响与风险

- Python 等运行时把管道写失败转化为异常，daemon 重启窗口内执行 `print` 的训练可能
  崩溃；接受为 MVP 限制并记录于设计第 11.2 节，M6 观察面复核时连同续捕一起评估
  log-keeper 方案。
- `SIG_IGN` 对极少数依赖 SIGPIPE 默认行为的程序是行为变化；Yori 托管的训练进程不
  属于此类（如需信号语义可通过 `signal()` 自行恢复）。

## 验证方式

M2 测试：spawn 的子进程 `SIGPIPE` 处置为忽略（子进程内自检并上报）；关闭管道读端后
子进程继续运行且写操作不致死。M4 恢复用例与 M6 跟随用例分别覆盖 offset 连续性与
续捕语义。

## M6 复核记录（2026-09-10）

观察面落地时按本决策"最迟 M6 复核"的要求重新评估续捕语义与 log-keeper 方案：

- **结论：维持本决策**。M6 的跟随回放采用 daemon 内存回看窗口（每流默认
  8 MiB，`LogStreamer`），重启后窗口为空，旧 offset 的重连以 `GAP` 帧显式
  跳到当前 offset——与第 2 条"重启窗口输出不可恢复、offset 不回退、不伪造
  空档"完全一致；恢复后的新输出经 LogPump 钩子按 LogSink 续写 offset 发布
  （第 3 条），观察面无需特殊迁移。
- log-keeper（常驻最小特权进程持有读端）仍维持 MVP 外对照方案：其消除的
  仅有重启窗口内的输出损失，代价是第二种守护对象与升级路径（复杂度接近
  `POST-09`）；M6 未出现改变该权衡的运行证据。
- Python 等运行时在重启窗口内 `print` 触发 `BrokenPipeError` 崩溃的限制
  维持不变，已在 `yori submit` 帮助与设计 11.2 明示。
